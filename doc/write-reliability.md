# 记账保存性能、连接释放与重试保护

## 分析与范围（2026-11-20）

本轮处理已确认的前三项优化：写入前备份不重复执行初始化、数据库连接明确关闭、首页支出／入账／转账与换汇防止重试重复入账。保留 WSL 启动及现有备份规则，不改原始账目、预算或冲销统计口径。

现状：`create_backup()` 每次先调用 `initialize_database()`；D 盘隔离副本三次测量的中位数为 1.67 秒，已初始化后跳过重复检查约 1.23 秒。`with connect()` 使用普通 SQLite 连接，仅管理提交／回滚，不关闭连接。首页虽然禁止连点，服务端仍将相同请求再次插入；响应丢失后重试无法识别上次是否已经成功。

## 备份与连接规则

1. 初始化及迁移集中在应用启动或显式初始化命令。备份仍在业务写入前生成完整 SQLite 快照，但不触发初始化、种子写入或迁移。
2. 备份以只读方式打开已存在的源账本，源文件缺失时失败，不创建空账本；备份失败阻止后续业务写入。备份保留及清理规则不变。
3. 应用连接使用统一的 SQLite Connection 子类：上下文正常退出时提交，异常时回滚，无论提交／回滚是否成功都明确关闭。连接不在退出后复用；已有手动管理的迁移仍负责 `finally` 关闭。
4. 升级检查及备份源、目标连接也采用相同关闭规则，保留 SQLite backup API 的一致性保障。原有 SQL、事务边界、外键校验和异常传播不变。

## 记账提交规则

此部分已实现，服务端回执和桌面恢复流程共同保护同一次记账提交。

1. 首页三种表单为每次新提交生成 UUID `request_id`；确认成功后下一笔使用新编号。相同金额、日期、账户的两笔真实消费仍可分别录入。
2. `POST /api/expenses`、`POST /api/incomes`、`POST /api/transfers` 接受可选编号，旧客户端省略时保持旧接口行为。其他独立维护流程仍使用各自的版本与事务校验。
3. 新增 `entry_requests` 表保存编号、操作类型、请求摘要、首次成功响应及时间。回执和流水／收入预算分配在同一写事务中提交或回滚；不提前保存成功标志。新表升级前创建 `finance-pre-entry-requests-*.db`，不为历史流水猜测或补造编号。
4. 同编号同内容返回首次结果并标记为重放，不新增流水或预算分配；同编号不同操作／内容返回冲突。先查回执，再备份；取得 SQLite 写锁后复查，保证同时到达的同编号请求也只写一次。并发的首次请求可能各自创建备份，但只有一个业务结果。
5. 回执不随流水删除或修改而删除，重试不恢复已删除流水。重放响应中的余额是首次保存时的余额，界面明确标注；当前余额仍从账户页查询。回执不参与收支统计和导出。
6. 明确失败且已回滚的校验请求不消耗编号，修改后可重新提交。网络错误、响应无法解析、超时和服务端异常不能当作保存失败，更不能自动换编号重记。

## 电脑页面恢复流程

- 提交前保留编号和原请求快照；当前标签页的 `sessionStorage` 保存待确认记录，刷新后可恢复。浏览器存储不可用时保留内存状态，并在发生不确定结果时说明需留在本页确认。
- 保存结果不确定时保留原输入并暂停编辑该模式，提供“重试并确认”及“查看流水”。重试沿用原编号、原内容；其他记账模式仍可使用，不自动重试写入。
- 请求异常、生成请求异常均恢复可操作状态。正常成功清理待确认记录、恢复原来的表单重置及余额提示；明确业务校验失败保留草稿供修改。
- 请求等待超过 30 秒时停止前端等待并转为待确认；这不代表服务端已经取消写入，必须沿用原编号重试。
- 新增请求和恢复请求使用同一保存流程，状态按支出、入账、转账分开；刷新后先恢复未确认草稿，再允许确认。

## 验证

- 隔离账本验证提交、回滚、提交失败均关闭连接；迁移和备份连接关闭；缺源文件和备份失败不产生业务写入；常规备份不执行初始化且可恢复已提交数据。
- API 验证三种记账的顺序重试、并发重试、不同内容冲突、不同编号同金额、预算原子回滚、重启后重试、删除流水后的重试，以及旧客户端兼容。
- 桌面浏览器模拟服务端已保存但响应丢失、刷新恢复、请求根本未送达、校验失败修改、连续真实同金额记录及收入拆分／转账；确认余额和实际流水笔数。
- 完成全套现有回归；正式账本只作为只读副本来源，不进行写入测试。

## 阶段验证

备份与连接管理：全套 164 项隔离测试通过（85.29 秒）。新增 6 项覆盖正常提交、异常回滚、提交失败、迁移和备份连接释放、缺失源文件，以及备份失败阻止写入；原预算、冲销、定存和导出回归通过。

加入提交回执后，全套 172 项隔离测试通过（95.71 秒）。新增 8 项覆盖顺序／并发重试、编号冲突、同金额独立提交、旧客户端、收入预算原子回滚、回执写入失败、重新初始化后重试、删除后不重建及升级备份幂等。`tests/entry_requests_browser.cjs` 验证桌面丢响应、未送达、刷新恢复、不同模式草稿、收入拆分、校验后修正和换汇重试。

复验旧收入拆分浏览器脚本时，预算行已有“收入来源”和“安排存储”两个按钮，旧脚本的无名称按钮选择器产生歧义。测试改为按“安排存储 / 查看来源”名称定位，不改变预算页面行为。修正后完整脚本通过，覆盖自动剩余切换、跨币种预览和保存、超配草稿、存储安排、流水编辑及历史额度替代。

在 D 盘相同位置的隔离账本上复测 3 次，完整备份中位数约 1.22 秒（优化前约 1.67 秒）。这是备份阶段耗时，不等于整个保存请求，也不作为其他设备的固定时延承诺；SQLite 完整备份仍在每次首次写入前完成。
