# 第六页：多预算计划与自定义栏目设计

设计日期：2026-10-01。状态：首版已实现；预算计划与实际流水分开保存。正式账本在下次启动时自动备份并升级。

2026-10-01 追加：未单独指定预算的实际支出自动按日常预算查询，包括历史消费；具体规则见 [预算归属设计](budget-attribution-and-settings-design.md)。这只改变第三页的统计归类，不扣减本页计划。界面统一层级、间距和配色，保留逐笔预算、总表、复制、历史及导出功能。

## 2026-10-02 修正：每个预算系统只有一种币种（当前规则）

上一版误将币种设计成月度预案下面的多个金额组，并锁住已保存币种。本次改为：**预算系统确定一种预算币种，各月份总额、二级存储分配均继承该币种**。不同预算系统可以使用不同币种；同一系统不能因消费币种不同而拆出另一份计划。

- 预算页每月只填一个总额；新系统首次编制时可在金额旁选择币种，之后自动沿用。设置页也可指定预算币种。
- 已有预算提供明确的“修改预算币种”入口。修改作用于该系统所有月份，操作前展示涉及月份及金额；以用户确认为准，预算历史版本保留原币种。用户已确认“更正币种、保留可见数字，由用户自行调整金额”，不使用实时汇率自动改写预算。
- 更正数字时按照目标币种重新编码最小单位，不能把分直接当元。目标精度不支持原数字时拒绝并指出月份，要求先调整该月金额，不静默四舍五入。修改有备份、全量计划版本检查，任一校验失败全部回滚；其他窗口的旧草稿不能覆盖新币种。
- 升级只增加系统币种配置。历史只有一种币种的系统自动继承；尚无计划的系统在首次设置或保存时确定。若旧系统确有多币种，原计划和统计完整保留，并标为待整理、暂停新增或改写，不静默合并金额或删除记录。
- 实际流水保持原始币种和金额，预算归属仍只选择预算系统。跨币种消费在最终比较时按汇率折成预算币种即可，不要求建立对应外币预算。第六页本次仍只管理计划，不新增自动扣预算或真实值比较计算。
- 验证：币种可修改、跨月统一、原数字及精度、历史快照、并发与回滚、旧账本备份及多币种兼容；电脑端历史月份、复制、设置、总表及导出；原始记账、账户余额、流水查询、冲销回归。

实现验证：51 项后端测试通过；隔离账本上的电脑端完整回归与历史月份 / 币种更正专项回归通过。设置页和预算页均可更正已有币种，未改写正式账本金额。

## 2026-10-02 多币种月度预案（已被上方规则替代）

本次调整解决同一用途需要分别创建人民币、港币计划的重复操作。电脑端以“预算系统 × 月份”展示和编辑一份预案：用途及月份只选一次，下面可添加多组“总预算金额＋币种”，每组内维护同币种的存储分配。币种不再放在预案身份选择中，二级分配自动继承对应金额组的币种。

- 月度列表把同用途的各币种合在一行，打开后一次加载全部币种；顶部币种筛选只影响查看，不裁掉编辑时的其他币种。
- 新增金额组时，在金额旁选择币种；同一预案每币种一组，重复币种被阻止。未保存组可移除、换币种；已有组保持币种及历史关联，可修改总额、分配和说明。暂不使用的已保存组可清空分配并将总额设零，不静默删除历史。
- 总额、已分配、待分配、金额精度均按币种独立计算；不得跨币种抵扣，也不自动换汇。总表及导出继续按币种展示。
- 一次保存完整月度预案。增加月度批量读写接口，复用原单币种校验与表结构；同一数据库事务内写入所有币种。任一币种超额、精度错误或版本冲突，整份预案不写入，前端保留全部草稿。若另一窗口新增了币种，也提示重新加载，避免漏存。
- 老单币种接口、历史记录、原明细 ID、标签、每币种版本及备份机制保留，无须迁移数据库。历史月份编辑、复制月份、历史查看及新增存储栏目同样支持多币种。复制会预览来源月的所有币种；目标已有而来源缺少的币种保留并明确提示。
- 桌面验证覆盖：一份预案多币种新建、分配继承、按币种统计、一次保存及失败回滚、旧数据兼容、复制历史月份、草稿保留、筛选后仍编辑完整预案。

## 2026-10-01 模型修正：预算用途与二级存储分配（旧币种规则已替代）

以下规则替代旧稿中“每个预算系统再建立一套用途”及“每种存储方式重复新增预算”的录入方式：

- **用途就是用户自定义的预算系统**。新增预算直接从已有系统选择，不再要求新增或选择独立用途栏目。
- **先录总预算，再分配存储方式**。一份计划以“预算系统 × 月份 × 币种”为键，填写总额；活期、定期、ETF 等作为下面的分配明细，可暂不分配或以后补充。分配只拆分该总额，不另加一次预算。
- 新增预算界面同时展示用途、月份、币种和总预算金额；同一用途、同月可分别创建人民币与港币计划，按币种独立统计，不自动折算或相加。
- 本月及累计总预算来自每份计划的总额；已分配来自二级明细；待分配＝总额－已分配。新模式禁止分配超过总额，并校验币种精度。
- 页面默认显示全部用途，交叉总表按“预算系统 × 存储方式”呈现。相同存储路径在总表合为一列，仍可查看各系统占比来源；不同币种分别成表。
- 九月等历史月份继续支持补录、追加分配及修改总额；保存修订同一份计划、保留版本并重算后续累计，不改变真实流水。
- 复用已有月计划、总额和明细表，无须删除旧用途或迁移账本。旧记录的用途标签作为历史说明保留；原总额为空时暂按原明细合计展示。若旧明细合计超出原填写总额，明确显示超额，编辑时由用户调整，不静默改金额。
- 原有接口保持兼容；新页面保存使用总额校验。旧版本、复制、存储栏目新增、导出和草稿保护继续可用。已有计划的系统、月份和币种固定，避免误将同一份预算移动到其他归属；新增时可选择任意启用系统和币种。

例：九月“慈善”预算 `1,000 CNY`，其中 ETF `600`、定期 `300`、待分配 `100`。新增时总额只填一次；之后调整二级分配时，预算总额仍为 `1,000`。

## 1. 首版范围（旧设计，以上方模型修正规则为准）

用户明确要求：

1. 第六页只有预算计划，不涉及真实值。
2. 每个月可以自行新增预算数值，也能修改当月计划。
3. 可以在页面上新增栏目、细化层级，提前安排每一笔预算的存储方式和使用方式。
4. 栏目管理和预算编辑均通过前端操作，不要求手工修改数据库。
5. 有总表查看 ETF 等存储方式的预算合计，以及其中分别安排给慈善、留存等用途的金额。
6. 支持多套可命名预算系统，例如日常预算、专项预算；分别编制月计划。实际收支可以单独标记预算归属，在第三页筛选。

本版用这些澄清替代上一稿的实际资金归属、投资份额、估值分摊、收益归属、对账和执行率设计。之前关于实际收益如何归属的待确认问题已不适用。

第六页独立记录计划，不读取真实收入、支出、账户余额、冲销净额或投资估值作为预算金额；不生成流水，也不要求先创建账户、录入收入或拥有相应资产。流水可引用同一个预算系统，供第三页查询实际消费；这种归属标记不会自动扣减或改写计划金额。预算默认项、分类映射、首页三种模式分离与统计规则见 [预算归属与设置设计](budget-attribution-and-settings-design.md)。

例如“慈善 × ETF：500 元”只表示计划将 500 元安排到这个组合，不表示已经买入 ETF 或拥有 500 元市值。

## 2. 两个独立、可自定义的维度

| 维度 | 回答的问题 | 示例 |
| --- | --- | --- |
| 存储方式 | 这笔预算准备怎样存放或配置？ | 活期、定期、ETF、股票 |
| 使用方式 / 用途 | 这笔预算准备拿来做什么？ | 日常生活、慈善、留存、学习 |

建议界面简称“存储方式”和“用途”。两者地位相同，都保存到数据库，各自形成一棵可管理的分类树，通过预算明细关联。预算系统是这两套栏目的上层容器；每个预算系统独立管理栏目和计划，可从另一系统复制配置，复制后独立修改。

一条预算明细的基本结构为：

```text
预算系统 + 月份 + 币种 + 存储方式 + 用途 + 预算金额 + 明细名称 / 备注
```

例如：

| 月份 | 存储方式 | 用途 | 明细名称 | 金额 |
| --- | --- | --- | --- | ---: |
| 2026-10 | ETF | 慈善 / 教育助学 | 助学储备第一笔 | 300 |
| 2026-10 | ETF | 慈善 / 教育助学 | 助学储备第二笔 | 200 |
| 2026-10 | 定期 / 三个月 | 留存 / 应急 | 应急计划 | 1,000 |

前两笔可以保留各自说明，矩阵中的“ETF × 教育助学”自动合计为 500。第一版允许多笔预算明细，不强制一个格子只能存一条记录。

同一笔金额通过两个维度查看，不存成两份分别累计。例如“慈善中的 ETF 500”与“ETF 中的慈善 500”是同一条计划。

## 3. 每月新增、修改与累计

### 3.1 建议采用“当月新增预算”作为录入值

用户每月创建一份计划，输入本月准备新增的预算金额，系统提供月度与累计两个视图。

```text
上月累计预算 = 起始月份至上月各月最新版本预算的合计
本月新增预算 = 本月预算明细的合计
截至本月累计预算 = 上月累计预算 + 本月新增预算
```

以“慈善 × ETF”为例：

| 月份 | 上月累计预算 | 本月新增预算 | 截至当月累计预算 |
| --- | ---: | ---: | ---: |
| 2026-10 | 0 | 500 | 500 |
| 2026-11 | 500 | 300 | 800 |
| 2026-12 | 800 | 200 | 1,000 |

输入十一月的 300，代表新增预算 300，不代表把累计目标改成 300。界面必须标明“本月新增”，不使用含糊的“金额”让这两种含义混淆。

所有累计数字均为**累计安排过的预算**，不代表尚未花掉的金额、实际持仓或资金余额。即使每月安排餐饮预算，年度合计也只是全年餐饮计划总额，不会根据真实消费自动扣减。

累计范围可选起始月份与截至月份；未来月份可提前编制，但不会加入更早月份的累计结果。没有创建计划的月份显示“未编制”，不能声称已有明确的零预算。

### 3.2 修改不会重复增加

- 将十一月 300 改成 350，是修订十一月计划，累计改为 850。
- 再次点击保存相同内容，不会再增加 350；保存需识别当前计划和明细 ID。
- 在十一月再新增一条 50，是另一笔新增预算，原有 300 保留，当月合计为 350。
- 把某条预算从 ETF 改为定期，是修改存储方式；该条金额保持一份，整体总额不变。
- 删除某条预算会从该月及其后的累计中移除其金额，保留修改记录。
- 修改旧月份会重算受影响的累计。保存前提示“将修订某月计划及后续累计”，历史版本仍可查看。

建议第一版明细金额非负；减少某月预算时直接改小或移除明细，不用负的新增金额来表示支出、亏损或提款。

如以后希望“保持旧月计划不变，但本月撤回或重新安排过去累计的预算”，需要独立的计划调整记录。本版不把这种动作混入新增预算，也不把累计视图当作可以随意覆盖的数字。

### 3.3 每月创建与复制

2026-10-01 历史月份编辑入口补充：编制月份可选择任意历史月份，选月后直接加载该月计划；提供“上个月 / 下个月 / 回到本月”快捷入口。九月未编制时可补录，已有计划时可修改原明细或追加新明细。编辑标题和保存按钮显示具体月份，保存仍修订该月唯一计划，并更新后续累计，不改写其他月份的明细。

切换前有未保存草稿时确认是否放弃；取消或加载失败时恢复原来的月份及筛选项，并保留草稿。切到早于累计起始月的月份时清空累计起始月，以便直接补录旧月。新记录、修改和追加均沿用已有版本检查及历史版本，无须迁移数据库。

“新建月份”提供：

1. 空白计划：选择月份、币种，逐笔添加预算。
2. 复制某月：复制栏目选择、明细说明与计划金额，预览后保存为新月份。

不会默认把上月累计金额再复制为本月新增金额。未保存的复制预览不进入统计；同一预算系统、月份、币种已有计划时，打开编辑，不重复建第二份并相加。月度与累计查询均限定所选预算系统，不混入另一套预算。

可选填写“本月预算总额”，完全由用户手填；不从实际收入自动取值。

```text
本月已安排 = 本月全部预算明细合计
尚未安排 = 本月预算总额 − 本月已安排
```

未填写总额时，只显示已安排数，不把总额当成零。已安排超过总额时显示“超出计划总额 X”，允许保存这一明确的计划差异，不宣称这是实际资金不足。

固定金额是第一版基础输入。比例分配若后续加入，只针对用户手填的计划总额生成可编辑明细，不依赖实际收入。

## 4. 新增栏目和更细粒度划分

### 4.1 页面提供的管理操作

在独立设置页提供“管理存储方式”和“管理用途”，第六页保留管理入口并带上当前预算系统，支持：

- 新增顶级项目。
- 新增子项目。
- 修改名称与说明。
- 调整显示顺序、展开或折叠。
- 停用项目，停用后不出现在新预算的可选项中，历史计划仍可查看。
- 删除从未使用且没有子项的项目；有预算引用时使用停用，保留关联。

预算明细选择器里也提供“＋新增存储方式 / 用途”，创建成功后立即可选，保留正在填写的金额和其他内容。

页面中新增一列或一行，本质上是新增一个分类记录。用户不需要写 SQL、修改数据库字段或修改前端代码。

### 4.2 层级例子

```text
存储方式                      用途
├─ 活期                       ├─ 日常生活
├─ 定期                       │  ├─ 餐饮
│  ├─ 三个月                  │  └─ 交通
│  └─ 一年                    ├─ 慈善
├─ ETF                        │  ├─ 教育助学
│  ├─ 宽基                    │  └─ 其他捐助
│  └─ 债券                    ├─ 留存
└─ 股票                       │  ├─ 应急
                              │  └─ 大额支出
                              └─ 学习
```

新预算填写在末级项目，父项目由子项汇总。折叠“慈善”时显示其合计，展开时显示助学和其他捐助；父合计不与子项再相加。

如果某个已有金额的末级项目后来增加子项，旧预算保留在原项目 ID 上，累计视图单列“原有未细分”部分。不能自动认为它全部属于某个新子项，也不能因新增子项使旧金额消失。用户可以打开相应月份，自行将旧明细拆分到子项，保存为该月的新版本。

同一父项目下不允许同名，同一个维度内禁止循环层级；不同父项目下同名时，选择器显示完整路径，例如“慈善 / 教育”和“个人 / 教育”。

### 4.3 改名、层级与历史

- 用稳定 ID 关联预算，改名不会让预算失去关联。
- 保存月度计划时保留该版本使用的栏目名称和层级快照，查看历史版本仍能看到当时的结构。
- 跨月累计默认按当前栏目结构整理，明确标为“按当前栏目汇总”；历史停用项目保留显示，不能被默认过滤掉金额。
- 改层级只改变当前汇总归组，不改变预算金额、月份或原币。
- 改名或调整层级前预览受影响范围；不需要用户手工迁移数据库。

## 5. 总表及直接编辑方式

建议总表默认用途为行，存储方式为列，也可切换行列。两种方向只是展示方式，数据库结构不变。

以下为某月计划金额示例，全部为手填预算：

| 用途 \ 存储方式 | 活期 | 定期 | ETF | 股票 | 用途合计 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 日常生活 | 3,000 | 0 | 0 | 0 | 3,000 |
| 慈善 | 200 | 300 | 500 | 0 | 1,000 |
| 留存 | 800 | 700 | 500 | 0 | 2,000 |
| 自用投资 | 0 | 1,000 | 2,000 | 1,000 | 4,000 |
| **存储方式合计** | **4,000** | **2,000** | **3,000** | **1,000** | **10,000** |

由此可知计划分给 ETF 共 3,000，其中慈善 500、留存 500、自用投资 2,000。行列合计是同一批明细的汇总，不能相加成 20,000。

支持两种查看范围：

- **本月新增预算**：矩阵显示所选月份明细的合计。
- **累计预算**：显示所选月份区间的累计计划，点击可按月份追溯。

点击单元格打开该组合的明细面板，可新增一笔、修改某笔或删除某笔。若格子内有多笔，不能通过直接覆盖合计数悄悄丢掉明细；需要明确编辑具体明细或使用可预览的批量替换。

空格可直接点“新增预算”；未填写和显式零预算在明细中区分。允许暂未决定某个维度，使用系统提供的“待定存储方式”或“待定用途”，其金额仍进入合计，之后在页面补全。

固定的月份、币种、名称、金额、备注之外，本轮支持自定义的是两套行列项目及子项。不把任意新文本字段、第三维度或公式列都做成表结构编辑器；将来需要其他维度时再设计。

## 6. 界面草案

页面建议名称改为“预算计划”，路径保持 `/budgets`。


每个汇总区明确显示月份范围、币种和“计划金额”。展示上同时保留总表与明细，支持先逐笔安排、再看汇总，也支持从矩阵格子直接补计划。

## 7. 数据库设计建议

### 7.1 两种栏目都入库，分别保存

采用关系表结构：预算系统表、两张栏目表、月计划表、明细表及版本记录，建表语句位于 `app/budget_schema.sql`。

| 表（建议名称） | 主要字段 | 职责 |
| --- | --- | --- |
| `budget_systems` | `id, name, sort_order, is_active, note` | 日常、专项等预算系统 |
| `budget_storage_methods` | `id, budget_system_id, parent_id, name, sort_order, is_active, note` | 某预算系统的存储方式及层级 |
| `budget_purposes` | `id, budget_system_id, parent_id, name, sort_order, is_active, note` | 某预算系统的用途及层级 |
| `budget_plans` | `id, budget_system_id, month, currency_code, total_minor（可空）, version, note` | 每系统、每月、每币种一份计划 |
| `budget_plan_items` | `id, plan_id, storage_method_id, purpose_id, title, amount_minor, sort_order, note` | 用户逐笔填写的预算金额 |
| `budget_plan_revisions` | `plan_id, version, snapshot, created_at` | 修改前后版本及当时的栏目名称、路径 |

金额只保存在明细中；矩阵、父项合计、月合计和累计结果由查询计算，不让用户另外维护重复的合计数。本月预算总额是用户独立填写的目标，所以单独保存，不能与明细合计再相加。

一个明细有一个存储方式 ID 和一个用途 ID。需要一笔预算拆成多个组合时，拆成多条明细；可以使用相同名称说明它们属于同一计划项目。

不设计 `活期金额`、`定期金额`、`ETF金额`、`慈善金额` 等固定数据库列，也不为每个月或每种栏目创建新表。新增“黄金”只会增加一条存储方式记录，所有查询和页面通过数据自动生成栏目。

两维都保存到 SQLite，而不是把其中一维写死在前端或只放在浏览器本地：这样刷新、换浏览器、备份恢复和历史汇总都能完整保留。

### 7.2 数据完整性与易维护性

- 预算系统、月份和币种组合唯一；预算明细引用同一系统中存在的栏目 ID，防止串用不同系统的栏目。父子栏目也必须属于同一系统。
- 同一个组合允许有多条有各自 ID 的明细；修改时定位明细 ID，不按金额猜测记录。
- 金额按币种最小单位保存整数，不使用浮点数直接累计。
- 用户新增、改名、停用、拆分等动作通过后端统一校验，同一次操作在一个数据库事务中完成。
- 更新使用版本检查，防止两个浏览器页面的旧内容互相覆盖；重复保存或重试不能重复插入预算。
- 首次保存和后续修改保留可查看版本，删除或修改预算有审计；复用项目已有备份约定。
- 删除被引用的栏目由外键阻止，界面提供停用，保留历史；系统“待定”项目不能删除。
- 版本快照用于保留历史，不替代主明细表，不把整套可查询预算仅存成一个不透明 JSON。

“数据库干净”主要来自统一数据结构、稳定关联和页面校验，不是让用户少建几个真正需要的栏目。

### 7.3 与现有表隔离

现有 `monthly_budgets` 是“月份 × 真实支出分类 × 币种”的生活支出预算，已经用于既有 Excel 对比。新的预算是“月份 × 自定义用途 × 自定义存储方式”，语义不同，建议使用独立命名的新表。

不将预算用途直接塞入现有 `categories`；不将计划 ETF、定期等创建成真实 `accounts`。真实流水可关联 `budget_systems` 作为统计标签，但不强制关联某月计划、计划明细或存储方式，不引入资金占用和估值计算。本轮不迁移、删除或改写已有 `monthly_budgets`，也不改变其导出逻辑。新预算导出使用明确的“预算计划”表名，避免与既有预算执行表混淆。

币种可复用 `currencies` 字典，但每份计划采用一个币种。跨币种累计分币种显示，不直接相加；第一版不依赖真实汇率。若未来需要折算计划，由用户明确设置预算汇率及其版本，另行设计。

## 8. 实现边界与验证场景

已实现独立预算服务 `app/budgets.py` 与前端 `static/budgets.*`、`static/budget-ui.js`，从服务端统一生成月度、累计和矩阵数据；模块不依赖实际收支统计服务或投资收益服务。设置管理位于 `static/settings.*`。矩阵支持展开明细、按一级栏目汇总与交换行列，点击金额可追溯或跳转到所属月份编辑；逐笔移除和修改在月明细表进行。

最小完整功能包括：月计划编辑、自定义两维栏目及层级、逐笔预算、本月 / 累计矩阵、修改版本、页面内栏目管理。不能只交付几个固定栏目就视为满足可自定义需求。

验收场景：

| 场景 | 预期 |
| --- | --- |
| 无真实账户或流水 | 仍可创建完整预算 |
| 十月新增 500，十一月新增 300 | 十一月累计 800，不需要再手填 800 |
| 将十一月 300 改为 350，再重复保存 | 累计 850，不会重复加 350 |
| 同月同组合添加 300 和 200 两笔 | 格子合计 500，展开仍有两笔 |
| 复制十月计划到十一月 | 预览后保存，复制的是当月明细，不是十月前全部累计 |
| 新增“黄金”或“慈善 / 助学” | 页面出现可选栏目，无需改数据库字段或代码 |
| 改名、停用已经被使用的栏目 | 历史引用完整，累计不丢金额，旧版本保留当时名称 |
| 已有父项目后来增加子项 | 旧金额显示为未细分，父子不会重复统计 |
| 将预算从 ETF 改到定期 | 总额不变，对应列合计重新分布 |
| 总额未填 / 明细超过目标总额 | 分别显示未设总额或超出计划，均不冒充真实资金状态 |
| 累计截至十一月，十二月已经编制 | 不包含十二月金额 |
| CNY 与 HKD 同期都有计划 | 分币种汇总，不直接混加 |
| 修改真实流水、冲销关系或投资估值 | 本页计划金额不自动变化 |
| 修改或新增预算 | 前五页实际收支、账户资产和投资数据不变化 |
| 同月编制日常和专项两份预算 | 彼此独立，栏目和累计金额不串用 |
| 实际支出标为日常预算 | 第三页可筛选，日常预算计划数不自动扣减 |

## 9. 已定方向与后续细化

已确认：纯预算计划、多预算系统、按月可新增数值、可自定义两维栏目、前端管理、可细分、可查看交叉总表；新增实际流水预算归属与第三页筛选，默认预算可配置。

建议规则：按“每月新增”录入并提供累计；金额优先逐笔固定数值；复制计划须先预览；使用稳定 ID、层级栏目与历史版本保持数据清楚。

后续可以按实际使用体验细化首批默认栏目、展示顺序、复制方式和币种。无需先确定真实账户、投资份额、收益分配或实际资金来源，即可进入纯预算页面的实现设计。

## 10. 首版接口与边界

- `GET /api/budget/config`：预算系统、栏目、默认项、映射、预设及配置版本。
- `POST /api/budget/config/{collection}`、`PUT /api/budget/config/{collection}/{id}`、`DELETE ...?expected_version=`：维护设置；集合为 `systems/storage/purposes/rules/presets`。
- `GET /api/budget/config/{collection}/{id}/impact`：用途或存储栏目的受影响月份及明细数。
- `PUT /api/budget/defaults`：分别选择支出和入账默认预算。
- `POST /api/budget/copy-catalog`：复制另一预算的两套栏目到仅含待定项的新预算，复制后独立维护。
- `GET/PUT /api/budget/plans/{system}/{YYYY-MM}/{currency}`：读取或保存月计划；更新携带 `expected_version` 和已有明细 ID。
- `GET .../revisions`：该月各已保存版本，包含当时名称和路径。
- `GET /api/budget/summary`、`GET /api/budget/export.xlsx`：参数为 `system_id/end_month/currency_code` 和可选 `start_month`，范围与币种一致。

月度目标和每月明细合计最多支持 `10^15` 个币种最小单位；累计在服务端用整数、前端用 BigInt 从十进制金额字符串求和。Excel 金额为数值单元格，用户填写的名称和说明按文本导出。

首版新预算预置待定栏目；初始“日常预算”额外预置活期、定期、ETF、股票及日常生活、慈善、留存。新预算可复制栏目后修改。复制月计划仅生成草稿；来源中已停用或已细分的栏目在新草稿中改为待定并提示，保存前可自行重新选择。历史版本只读，当前版本允许修改和清空明细。

验证使用临时数据库：`tests/test_budgets.py` 覆盖迁移、版本、精度、层级、跨预算校验、统计与冲销；`tests/budget_browser.cjs` 配合 `tests/budget_browser_server.py` 验证实际页面操作。正式账本未用于测试。
