# 流水查询汇总与工资支出分类设计

## 背景与问题

本次需求来自 `temp.log`，包含两个问题：

1. 第三页“账户与流水”的“流水查询”只有分页后的逐笔结果和总笔数，缺少按所选日期、流水类型和其他筛选条件计算的金额汇总。用户无法快速看到各流水类型的金额，也无法看到多个流水类型合并后的整体资金流动。
2. 现有“工资/劳务”只属于收入分类，适用于本人收到工资或劳务报酬。给他人发工资属于支出，首页的支出分类中没有对应项目。

当前的 `GET /api/transactions/search` 已支持多账户、日期、多个流水类型、多个分类、关键词、手工调整和待核实状态筛选，但返回内容只有：

- 当前页流水。
- 分页信息和符合条件的总笔数。

它没有返回不受分页影响的金额合计。另一方面，现有 `GET /api/transactions/analysis` 只支持单一流水类型，并且服务于日历、直方图和行为统计，不能作为多类型金额汇总的替代方案。

## 设计目标

在不改变现有流水表、账户余额计算和汇率快照的前提下：

1. 为流水查询增加“查询汇总”，展示同一筛选条件下全部命中流水的笔数和金额。
2. 同时展示：
   - 所有已选流水类型合并后的资金流入、流出和净流动。
   - 各流水类型各自的笔数和资金流动。
3. 保留 CNY、HKD、USD 等原币种的分项统计，同时按系统已保存汇率提供 CNY 与 HKD 两种统一计价的合计。
4. 当选择单个账户时，汇总只计算该账户一侧的资金变动，能够反映该账户在筛选范围内的流入、流出和净变动。
5. 增加一个明确的支出分类“工资/劳务支出”，用于给他人发工资、支付劳务费或兼职报酬。

## 非目标

本次不做以下功能：

- 不请求实时汇率，也不在查询时补写或覆盖历史汇率快照。
- 不在多账户、分类或关键词筛选下伪造“期初余额”和“期末余额”。
- 不新增“发工资”这种独立流水类型；它仍是一笔普通支出。
- 不新增分类管理前端。个人项目仍可按 [数据库手工维护说明](database-manual.md) 直接维护分类。

## 为什么不能直接显示“期初余额 / 期末余额”

账户明细中的期初、当前余额和每笔余额后值，来自一个确定账户的完整历史流水。流水查询则可以同时筛选多个账户、多种币种、某个分类、关键词或某种流水类型。

例如，用户查询“八达通账户，2026-09-01 至 2026-09-30，分类为餐饮”时，餐饮流水的合计不等于八达通账户的期末余额变化，因为该账户可能还有交通、充值或手工调整等被筛选条件排除的流水。

因此，流水查询新增的区域命名为“查询汇总”，展示**筛选结果本身的资金流**，而不是账户余额：

- 流入：命中流水中进入统计范围账户的金额。
- 流出：命中流水中离开统计范围账户的金额。
- 净流动：流入减流出。

若需要查看真实账户余额和完整余额轨迹，继续使用同页“账户明细”。

## 查询汇总口径

### 启用条件

查询汇总仅在同时选择完整的开始日期和结束日期时展示和计算：

1. 开始日期不得晚于结束日期。
2. 其他筛选条件与逐笔结果完全一致。
3. 分页不影响汇总，汇总覆盖所有命中流水。

未选择完整日期时，逐笔查询仍可正常使用；汇总区域显示“请选择完整日期范围后查看金额汇总”，不计算全历史金额，避免误把全部历史流水当成某一期间总额。

### 原币种明细与统一计价合计

查询汇总先以流水真实币种展示，按币种分组，作为最容易核对的明细。例如：

| 币种 | 流入 | 流出 | 净流动 |
| --- | ---: | ---: | ---: |
| CNY | 8,000.00 | 5,000.00 | +3,000.00 |
| HKD | 0.00 | 820.50 | -820.50 |

在原币种表格之后，增加“统一计价合计”，将全部可换算资金腿分别折算为 CNY 和 HKD：

| 计价货币 | 流入 | 流出 | 净流动 |
| --- | ---: | ---: | ---: |
| CNY | 8,737.00 | 5,738.25 | +2,998.75 |
| HKD | 9,430.81 | 6,190.00 | +3,240.81 |

这两行是同一批流水分别用两种计价货币表达的结果，不应再将 CNY 行和 HKD 行相加。原币种明细与统一计价合计同时展示：

- 原币种明细用于逐项对账，并完整保留每种货币的流入和流出。
- CNY 与 HKD 合计用于快速理解多币种流水的总规模和净流动。

### 汇率与换算规则

统一计价只读取 `daily_cny_exchange_rates` 中已保存的系统汇率快照，不会因为打开流水查询而联网、创建备份或改写任何历史数据。规则与“流水详情”保持一致：

1. 优先使用流水日期当天的汇率快照。
2. 当天没有快照时，使用数据库中日期距离最近的可用快照；距离相同则优先较早日期。
3. 没有任何快照，或原币种不属于 CNY、HKD、USD 时，该资金腿仍保留在原币种明细中，但不纳入统一计价合计。

换算公式如下，其中 `hkd_cny_rate` 和 `usd_cny_rate` 是系统保存的同日或最近快照：

| 原币 | CNY 计价 | HKD 计价 |
| --- | --- | --- |
| CNY | 原金额 | `CNY / hkd_cny_rate` |
| HKD | `HKD * hkd_cny_rate` | 原金额 |
| USD | `USD * usd_cny_rate` | `USD * usd_cny_rate / hkd_cny_rate` |

页面必须同时显示两种计价的覆盖情况，包括原计价币种直接纳入资金腿数、当天快照换算资金腿数、邻近日期快照换算资金腿数、未纳入统一计价的资金腿数及其币种。这样 EUR、JPY 或缺少快照的历史流水不会被静默忽略。

### 账户范围

#### 未选择账户

查询范围是全部账户。每笔命中流水的两端都参与汇总：

- 支出：记入来源账户币种的流出。
- 入账：记入去向账户币种的流入。
- 转账、换汇、券商入金、券商出金：来源端记流出，去向端记流入。
- 调整：调减记流出，调增记流入。

同币种转账在全部账户范围下会同时产生同额流入和流出，净流动为零。这是正确的资金路径展示，不代表收入或支出。

#### 选择一个账户

查询范围改为所选账户。对每笔命中流水，只统计该账户所在的一侧：

- 所选账户是来源账户：只计流出。
- 所选账户是去向账户：只计流入。

例如，查询“支付宝余额”时，“支付宝余额 -> 支付宝基金”的定投只显示支付宝余额的流出；不会把支付宝基金的流入再计入同一账户汇总。这样“净流动”才能表示所选账户在筛选结果中的实际变动方向。

### 流水类型汇总

“查询汇总”包含两个层级：

1. **全部类型合计**：所有命中流水合并后的原币种流入、流出和净流动，以及 CNY、HKD 两种统一计价的流入、流出和净流动。
2. **按类型明细**：对每一种已选或实际命中的流水类型，显示：
   - 流水类型名称。
   - 该类型的笔数。
   - 按原币种列出的流入、流出和净流动。
   - CNY、HKD 两种统一计价的小计。

当用户未勾选流水类型时，表示全部类型；按类型明细显示实际命中的类型。当用户勾选多个类型时，按类型明细至少显示所有已勾选类型，即使其中某个类型因其他筛选条件而为 0 笔。

类型金额的方向如下：

| 流水类型 | 流出 | 流入 |
| --- | --- | --- |
| 支出 | 支付账户金额 | 无 |
| 入账 | 无 | 到账账户金额 |
| 转账 | 转出账户金额 | 转入账户金额 |
| 换汇 | 换出币种金额 | 换入币种金额 |
| 券商入金 | 转出账户金额 | 券商账户金额 |
| 券商出金 | 券商账户金额 | 转入账户金额 |
| 调整 | 调减金额 | 调增金额 |

“笔数”按交易记录计数，而不是按资金腿计数。一笔转账在金额层面有一笔流出和一笔流入，但在类型笔数中仍只算 1 笔。

## 前端设计

在“流水查询”筛选表单与“查询结果”表格之间增加“查询汇总”区域。

区域结构：

1. 标题“查询汇总”，右侧显示日期范围和命中总笔数。
2. “全部类型合计”中的“原币种明细”表格：币种、流入、流出、净流动。
3. “全部类型合计”中的“统一计价合计”表格：计价货币（CNY、HKD）、流入、流出、净流动和汇率覆盖提示。
4. “按流水类型”表格或折叠分组：类型、笔数、原币种明细，以及 CNY、HKD 两种统一计价小计。
5. 无完整日期时显示约束提示；完整日期但没有流水时显示 0 笔，不显示金额行。

金额格式：

- 保留现有币种的小数位。
- 净流动显示显式正负号，例如 `+35.00 HKD`、`-120.00 CNY`。
- CNY 与 HKD 的统一计价合计明确标注“按已保存汇率折算”，并显示汇率覆盖情况。
- 不显示未注明计价货币的“总金额”字段。

流水详情（日历、每日金额直方图和统计）继续位于查询结果下方，仍只在完整日期范围加单一流水类型时启用。查询汇总与流水详情可以同时存在，职责不同：

- 查询汇总：支持多类型，原币种资金流核对。
- 流水详情：单一类型，统一换算为 HKD 后分析每日金额分布。

### 查询实现

实现时从现有 `search_transactions` 中抽取一套共享的筛选构造逻辑，确保明细、总笔数和汇总使用完全相同的条件，避免三个 SQL 查询出现条件漂移。

汇总查询使用以下步骤：

1. 以当前筛选条件生成 `filtered_transactions` 公共表达式。
2. 对来源账户生成一条“流出资金腿”，对去向账户生成一条“流入资金腿”。
3. 未选择账户时保留全部资金腿；选择账户时只保留 `account_id` 等于所选账户的资金腿。
4. 按 `transaction_type`、币种汇总流入和流出金额。
5. 单独按 `transaction_type` 统计交易记录数，避免转账被计为两笔。
6. 对每条可换算资金腿按其流水日期查找当天或最近系统汇率，并分别累计 CNY、HKD 统一计价结果。
7. 将原币金额按 `currencies.decimal_places` 格式化，将 CNY、HKD 统一计价结果按两位小数格式化后返回。

汇总不写入数据库、不创建备份、不联网获取汇率。

## 工资/劳务支出分类

### 分类定义

新增以下根级支出分类：

| kind | name | sort_order | 适用场景 |
| --- | --- | ---: | --- |
| `expense` | `工资/劳务支出` | 95 | 给他人发工资、支付劳务费、兼职报酬或雇佣服务报酬 |

当前已有的收入分类 `工资/劳务` 保持不变，用于本人收到工资或劳务收入。

不复用同一个分类记录的原因是 `categories.kind` 与流水类型有数据库约束：

- 收入流水只能引用 `kind = 'income'` 的分类。
- 支出流水只能引用 `kind = 'expense'` 的分类。

使用“工资/劳务支出”这个名称，而不是在收入和支出中创建两个同名“工资/劳务”，可以避免第三页跨收入/支出分类筛选时出现难以区分的重复选项。

### 初始化与使用

在 `app/database.py` 的 `CATEGORY_SEED` 增加该分类即可。初始化使用 `INSERT OR IGNORE`：

- 新建数据库时自动创建。
- 现有数据库在下次启动后自动补入。
- 已有流水和已有分类不受影响。

首页支出表单、流水修改表单和流水查询分类筛选都已经从 `/api/categories?kind=expense` 或现有分类接口动态读取分类，因此不需要为该分类新增专用表单字段或专用 API。

创建流水时：

- 类型选择“支出”。
- 支付账户选择实际付款账户。
- 支出分类选择“工资/劳务支出”。
- “商户或对象”填写收款人或服务方；备注可填写工资月份、工时或合同说明。

## 验收标准

### 查询汇总

1. 选择完整日期，查询汇总显示全部命中记录，而不受 50 条分页限制。
2. 同时勾选“支出”和“入账”时，能分别看到两种类型的笔数和资金流，并看到两者的合计。
3. 同时存在 CNY、HKD、USD 时，金额按原币种分行展示，并同时显示按系统汇率折算的 CNY、HKD 两种合计。
4. 查询单个账户时，一笔从该账户转出的转账只计流出；一笔转入该账户的转账只计流入。
5. 全部账户查询中，同币种转账同时计入流入和流出，净流动为零。
6. 未选择完整日期时，不计算全历史金额，并给出明确提示。
7. 汇率缺失或不支持的币种仍显示在原币种明细中，并在 CNY、HKD 统一计价区显示未纳入数量和原因。
8. 分页、编辑、删除、标记后重新查询时，汇总和表格同步刷新。

### 工资/劳务支出

1. 新数据库和已有数据库初始化后，都存在启用状态的“工资/劳务支出”支出分类。
2. 首页支出表单可选择该分类并创建支出流水。
3. “工资/劳务”收入分类仍可创建入账流水。
4. 不能用收入分类创建支出，也不能用“工资/劳务支出”创建入账，现有数据库和后端校验继续生效。

## 测试计划

新增或扩展冒烟测试：

1. 创建同一日期范围内的 CNY 支出、HKD 支出、CNY 入账、同币种转账和 CNY/HKD 换汇。
2. 调用多类型流水查询，断言：
   - 分页总笔数与汇总总笔数一致。
   - 类型笔数按交易记录而非资金腿计数。
   - 各原币种流入、流出和净流动符合预期。
   - 使用当天与邻近日期系统汇率折算的 CNY、HKD 合计符合预期。
3. 带 `account_id` 调用，断言转账只统计所选账户对应的一侧。
4. 使用 EUR 或没有任何汇率快照的日期，断言原币种明细保留该流水，并在统一计价覆盖信息中显示排除原因。
5. 仅传开始日期或仅传结束日期，断言返回不可用汇总提示。
6. 运行初始化后查询 `categories`，断言存在 `expense / 工资/劳务支出`。
7. 用该分类创建支出成功；将它作为收入分类提交时被拒绝。

## 实施顺序
